# C++ コーディング規約

この文書は ControlBarGraph のファームウェアへ適用する C++ の実装規則です。Arduino / ESP32
固有の制約を踏まえつつ、読みやすさ、安全性、テスト容易性、保守性を優先します。既存コードを
変更する際は、目的外の全面的な書き換えを行わず、触れた範囲から本規約へ段階的に合わせます。

## 実装開始前のブランチ更新

コードを書き始める前に、現在の作業へ最新の `develop` を取り込みます。古いベースのまま実装を
始めて競合や修正済み不具合を持ち込まないため、次の順序を守ります。

1. `git status --short --branch` でブランチと作業ツリーを確認する。
2. 未コミットの変更がある場合は、別の変更と混ぜずにコミットするか安全に退避する。
3. `git fetch origin develop` でリモート追跡情報を更新する。
4. チームとブランチの運用方針に従い、`origin/develop` を現在の作業ブランチへ merge または
   rebase する。共有済みブランチを無断で rebase しない。
5. 競合があれば、双方の意図と現行仕様を確認して解消する。単に一方を選んで終わらせない。
6. 取り込み後の差分を確認し、少なくともベースラインのビルドと必要なテストを実行してから
   新しいコードを書く。

リモート `origin`、`develop`、またはネットワークが利用できず更新できない場合は、最新であると
仮定して実装を進めません。実行したコマンドと制約を記録し、更新方法を確認してから再開します。
ドキュメントだけを変更し、コードを一切書かない作業ではこの更新を必須としませんが、既存の
作業ツリーと文書の正本は必ず確認します。

## 基本原則

- 意図が明確な単純な設計を選び、将来使うかもしれない抽象化を先回りして追加しない。
- 1 つの関数、クラス、モジュールには 1 つの責務を持たせ、ハードウェアアクセス、状態遷移、
  入力解析、通信処理を分離する。
- 動作するコードを仕様の代わりにせず、公開契約と安全上の前提を Doxygen コメントで記録する。
- 警告を放置せず、暗黙変換、符号、桁あふれ、未使用値、到達不能コードを確認する。
- GPIO 27 の出力や LED の状態など、外部から観測できる動作を変更するときは要求仕様、設計資料、
  実機検証記録を同じ変更単位で更新する。

## Doxygen docstring

### 対象

すべての関数、メンバー関数、コンストラクター、デストラクター、演算子、関数テンプレート、
クラス、構造体に `/** ... */` 形式の Doxygen コメントを付けます。`setup()`、`loop()`、内部
リンケージの補助関数、private メンバーも対象です。型エイリアス、列挙型、定数、データメンバーは、
名前だけでは用途、単位、範囲、所有権が明らかでない場合に同形式で説明します。

### 1 か所だけに記述する規則

説明本文の正本は 1 か所だけに置きます。

- ヘッダーに宣言がある公開 API は、宣言の直前を正本とし、`.cpp` の定義には同じ説明を
  書かない。
- `.cpp` にしか存在しない関数や型は、その宣言または定義の直前を正本とする。前方宣言がある
  場合は前方宣言側へ書き、定義側では繰り返さない。
- クラスの責務はクラス宣言に、各メンバー関数の契約は各メンバー宣言に書く。クラス説明へ
  全メンバーの詳細を重複記載しない。
- README、要求仕様、Doxygen の間で長い説明を複製しない。Doxygen から設計判断が必要な場合は
  `@see docs/requirements.md` のように正本を参照する。

基底クラスや既存 API と契約が同じオーバーライドでは、説明をコピーせず `@copydoc` または
`@inheritdoc` を使用します。振る舞いを追加する場合は、継承元の契約を参照したうえで差分だけを
追記します。コピー＆ペーストした説明を複数箇所で維持してはいけません。

```cpp
#include <cstdint>

/**
 * @brief 指定速度を検証し、パルス出力へ反映する。
 *
 * @param speed 速度。単位と許容範囲は設定ファイルの定義に従う。
 * @return 適用できた場合は true、出力を変更しなかった場合は false。
 * @pre パルス出力の初期化が完了していること。
 * @post 失敗時は直前の有効な出力を維持する。
 */
bool applySpeed(std::int32_t speed);

// 定義側では docstring を繰り返さない。
bool applySpeed(std::int32_t speed) {
    // 実装理由が自明でない箇所だけに通常コメントを書く。
}
```

```cpp
class InputHandler {
public:
    /** @brief 入力を 1 回処理する。 */
    virtual void poll() = 0;
};

class SerialInputHandler final : public InputHandler {
public:
    /** @copydoc InputHandler::poll */
    void poll() override;
};
```

### 記載内容

docstring には必要に応じて次を含めます。

- `@brief`: 何をするか。実装手順ではなく責務を書く。
- `@param`: 各引数の意味、単位、許容範囲、null 許容性、所有権。
- `@return`: 戻り値の意味。真偽値やエラー値が何を保証するか。
- `@pre` / `@post`: 初期化状態、排他条件、成功・失敗後に維持される状態。
- `@note` / `@warning`: タイミング、GPIO、割り込み、ブロッキング、安全上の制約。
- `@see`: 詳細の正本となる要求仕様、設計文書、関連 API。

関数名を日本語へ言い換えるだけの説明や、コードを逐語的に説明するコメントは避けます。通常の
行コメントは「何をしているか」ではなく、回路制約、データシート上の理由、アルゴリズム選択など
コードから読み取れない「なぜ」を説明する場合だけに使います。

## 型と値

- ビット幅や範囲が重要な GPIO、周波数、ADC 値には `<cstdint>` の固定幅整数型を使う。
- 符号付き・符号なしを混在させない。外部入力は十分な幅の型で解析し、範囲確認後に狭い型へ
  明示変換する。
- 単位の異なる値を同じ変数で使い回さず、`speed`、`frequencyHz`、`timeoutMs` のように単位を
  名前または型で明確にする。
- コンパイル時に確定する値は `constexpr` とし、変更可能なグローバル変数を避ける。
- 関連する選択肢はマクロや裸の整数ではなく `enum class` で表す。
- C 形式キャストを避け、検証後に `static_cast` など意図に合う C++ キャストを使う。
- `auto` は右辺から型と意味が明白な場合に使い、整数幅や所有権を隠す場合は明示型を使う。

## 命名と構成

- Arduino / ESP32 API の既存表記を尊重しつつ、プロジェクト内では同じ概念に同じ名前を使う。
- 型は役割が分かる名詞、関数は動作が分かる動詞、真偽値は `is`、`has`、`can` など状態が分かる
  名前にする。意味のない `data`、`tmp`、`value` を広いスコープで使わない。
- 変数のスコープと寿命を必要最小限にし、内部実装は匿名 namespace またはクラスの private
  メンバーへ閉じ込める。
- ヘッダーは自己完結させ、使用する型のヘッダーを直接 include する。include guard または
  `#pragma once` を用い、ヘッダーで `using namespace` を使用しない。
- include の循環を避け、完全型が不要なら前方宣言を検討する。ただし所有権や依存関係を
  不明瞭にするためだけの前方宣言は行わない。
- 1 行に複数の文を書かず、インデントは 4 スペースとする。条件分岐とループには、1 文だけでも
  波括弧を付ける。

## 関数とクラス設計

- 関数は短く保ち、入力検証、状態変更、ハードウェア出力の各結果を追跡できる構造にする。
- 引数は変更しない小さな値なら値渡し、大きなオブジェクトなら `const&` を基本とする。null が
  不要ならポインターではなく参照を使う。
- 戻り値を捨てると危険な検証・初期化関数には `[[nodiscard]]` を検討する。
- オーバーライドには `override`、継承させない型や仮想関数には必要に応じて `final` を付ける。
- 基底クラスを介して破棄する型には virtual デストラクターを用意する。継承が不要なら合成を
  優先する。
- 不変条件はコンストラクターで成立させる。初期化に失敗し得るハードウェア資源は、明示的な
  `begin()` と結果型で扱い、半端な初期化状態を通常動作へ渡さない。
- コピーやムーブが不適切な GPIO・通信・所有資源の型は、該当操作を `= delete` して意図しない
  複製を禁止する。

## 所有権、メモリ、文字列

- 所有権は型とスコープで明確にし、手動の `new` / `delete` を避ける。固定寿命の構成要素は
  静的配置または値メンバーを優先する。
- 所有しない参照やポインターは、参照先の寿命と null 可否を docstring に記載する。
- 周期処理で動的確保を繰り返さない。長時間稼働時の断片化を避けるため、上限付き固定バッファ、
  `std::array`、長さを明示したビューを優先する。
- Arduino `String` を無制限に連結せず、シリアルや HTTP 入力には最大長を設ける。終端、切り詰め、
  不正 UTF-8 や数値変換失敗を明示的に扱う。
- バッファの容量と実データ長を分けて管理し、境界外アクセスと整数オーバーフローを API 呼び出し
  前に検査する。

## エラー処理と入力検証

- ESP32 / Arduino のビルド設定で例外が無効な可能性を前提とし、通常の失敗を例外に依存させず、
  `bool`、`enum class`、結果構造体など明示的な結果で返す。
- 戻り値を必ず確認し、失敗を成功として継続しない。回復可能な失敗と起動停止エラーを区別する。
- Web、シリアル、ADC の入力は共通の検証経路へ集約し、解析と状態変更を分離する。検証完了前に
  GPIO、LEDC、デモ状態、保存済み設定を変更しない。
- 負値、ゼロ、上限、演算オーバーフロー、NaN、無限大、LEDC の周波数・分解能制約を考慮する。
- エラーには処理名と原因を含めるが、Wi-Fi パスワードなどの秘密情報はログへ出力しない。

## 組み込み・リアルタイム処理

- `loop()` 内の各処理は短時間で戻し、長い `delay()`、無期限待機、ブロッキング読み取りを避ける。
  タイムアウトと `millis()` 等の時刻差分で状態機械を進める。
- 時刻の差分はカウンターのラップアラウンドを許容する符号なし減算で判定し、絶対時刻の単純比較を
  避ける。
- ISR は最小限にし、ログ、動的確保、ブロッキング API、複雑な状態遷移を実行しない。ISR と
  通常処理の共有データには、`volatile` だけで排他性が得られると考えず、ESP32 のクリティカル
  セクションや適切な atomic／キューを使う。
- ボタンのデバウンス、ADC のノイズ抑制、LED 点滅、デモ更新を非ブロッキングで処理する。
- ハードウェア API は一元化し、テスト可能な計算・解析ロジックから分離する。
- GPIO は安全な初期値を先に設定してから出力へ切り替え、初期化失敗時も仕様で定めた安全状態を
  維持する。
- ログの頻度を制限し、周期処理や Web 応答をシリアル出力で飽和させない。

## `constexpr` 設定とハードウェア定義

- Wi-Fi、mDNS、全ピン番号、タイムアウト、速度範囲などの設定は、要求仕様で定めた 1 つの設定
  ファイルへ名前付き `constexpr` として集約する。
- 数値リテラルを GPIO API の呼び出し箇所へ重複記述しない。LEDC channel、分解能、デューティ比、
  ポート番号にも意味のある名前を付ける。
- `static_assert` で表現できるピン重複、範囲の大小関係、バッファ容量などはコンパイル時に検証する。
- 秘密情報を実運用値のままコミットしない。例示値とローカル設定の分離方法を README に記載する。

## 状態管理と並行性

- 手動入力、デモ、通常入力を複数の独立した真偽値だけで表現して不正な組み合わせを作らず、
  状態と遷移を明示する。要求仕様の優先順位を 1 か所で適用する。
- 状態を変更する関数と状態を参照する関数を区別し、読み取り操作が暗黙に出力を変えないようにする。
- Web、シリアル、ボタンが同じ状態を更新する場合は、単一の更新 API を経由させる。
- 複数タスクやコールバックを導入する場合は、共有可変状態を最小化し、所有タスク、同期方法、
  コールバックの実行コンテキストを docstring に明記する。

## テストとレビュー

- 速度―周波数変換、ADC 線形変換、コマンド解析、状態遷移をハードウェアから分離し、境界値を
  ホストまたは PlatformIO の自動テストで検証できるようにする。
- 正常値だけでなく、最小値、最大値、範囲外、ゼロ、負値、最大長、タイムアウト、カウンターの
  ラップアラウンドを試す。
- ハードウェア変更では、対象ボード、入力、期待値、シリアルログ、GPIO 27 と LED の実測結果を
  記録する。
- コミット前に少なくとも `pio run` と `git diff --check` を実行する。環境上実行できない検証は
  成功扱いにせず明記する。
- レビューでは docstring の有無だけでなく、正本が 1 か所か、契約と実装が一致するか、継承参照が
  正しいか、失敗時に安全な状態を維持するかを確認する。
